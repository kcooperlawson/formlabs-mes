# Formlabs MES — Changelog

Running log of what's changed in the app, newest first. One entry per day I worked on it. These were long days (6–8 hours each), and most of what's below happened in clusters — a fix, the thing it broke, and the decision that came out of it usually belong together, so they're written together.

Entries before August 31 have been written back up from the release notes I cut at the time, which were short and full of shorthand. Several of those days carried two or three releases inside them; where that happened it's noted under the heading, since it's the honest explanation for why some days are long.

## 3.12 — Friday, September 4, 2026
**One switch decides what this is: a logging system or an execution system. Everything else followed from admitting the log is the product.**

The worry I started the day with was that management would look at eighteen screens and shut it down for being too much. The honest response was not to hide anything — it was to notice that almost none of it is being proposed. The log is the system; the rest is settings. Most of today was making the software and the documents say that, and removing the two places where they said more than was true.

- **The application worked with no work orders and told the operator it was broken for it.** A plant that had not set one up got a heading with a manager's name over an empty space, an info box telling it to go and find a manager, a yellow warning on every log about a run that did not match, a warning-triangle toast after every submit about a progress bar it did not have, and a floor display announcing "No Work Orders configured" to a room, all shift. Five different sentences saying the same untrue thing: something is missing here. Nothing was.
- **`simple_mode` (Alembic `0009`), on by default including for the row that already exists.** Work orders are one way to run a plant and the log does not need them, so this makes that a stored fact rather than a guess. On, the operator terminal is station, material, lot, counts. Off, every work-order screen returns exactly as it was, and nothing entered is lost in either direction.
- The frame is blanked once at the top of the operator page rather than the setting being tested at each of the four places that read it. That is not tidiness — it is the reason a stale run left open in the database cannot raise **DO NOT POUR** on a terminal that has no way to show the operator what it is talking about. With no run to compare against the lot check records instead of comparing, which is still the whole traceability answer and needs nobody's setup. There is a browser test whose last assertion is exactly that: four open runs in the database, all hidden, and a deliberately wrong code that must not stop the pour.

- **A manager is now the administrator, unless the plant says otherwise.** The separate IT role was the other thing a small plant does not have. It is folded into the same switch, because the two go together in practice: a plant small enough not to dispatch work is a plant small enough not to have an IT person. As a **logging system** a manager holds the whole console — accounts and PIN resets, pumps, resins, plant settings, backups, cleanup. As an **execution system** work orders come back and administration goes back to administrator accounts.
- The rule is one function. `crud.can_administer` takes the role and the mode and answers; `database.role_can_administer` supplies this plant's mode from the cached settings; eleven call sites across eight files ask it instead of comparing a string to `"admin"`. Eleven copies of a permission check is how one of them ends up disagreeing with the other ten.
- **Two guards, because this is a privilege change.** Switching to an execution system while no administrator account exists would leave nobody able to reach the console, including to switch it back — that save is refused, every other setting on the form still goes through, and the message says what has to exist first. And a manager who arrives at the console is told why they have it and what takes it away; finding the restore-a-backup button without having been told you had it is a bad way to learn the scope of your access.
- New `tests/test_roles.py` puts every combination through the rule without a database, including the half that is easy to leave untested — a manager must be **refused** in execution mode — plus the shapes the value actually arrives in: `1`/`0` from an INTEGER column, `None` from a row nobody has touched, and stray case and whitespace off a roster screen.

- **The sign-in screen follows the mode.** It read SCADA TERMINAL over MANUFACTURING EXECUTION SYSTEM — the largest claim the application makes, on the first screen anyone sees, and in a plant running this as a record not a true one. As a logging system it now reads POURING LOG over RESIN POURING · PRODUCTION RECORD, and the original wording returns with the mode that earns it.

- **The shift handover is gone (Alembic `0010`).** It produced four whole-day figures as a PDF — poured, packed, work in progress, scrap — and emailed them. Every one of those is on the landing screen broken down by station, operator, resin and shift, which the report was not: it filtered by *date*, so on a two-shift plant the second shift's "handover" silently included the first shift's work, and a night shift crossing midnight split across two reports. The incoming lead arrives before the shift and opens the app; he was always going to see more than the report could tell him. It was also the only feature in the application that needed an outside credential and outbound SMTP, which made the least useful screen the most expensive one to set up. The page, the `handover_emails` column, the admin field and the `fpdf` dependency all went with it.
- **Found next door while removing it:** the Google Sync page had an "Automation Trigger Preference" offering a manual push, an auto-sync on shift handover, and a scheduled webhook. Only the first existed — the chosen value was never read except to word the spinner, so the other two produced the same manual push with a different sentence over it. One of its options named the screen I had just deleted. A control that appears to configure something and does not is worse than no control; it is gone, and the caption now says every push is manual and on demand.

- **Two real bugs fell out of the mode work.** The recorded-lot message read back `L-L-2411A0742` — the prefix doubled, because the read-back used the raw field while the caption above promises the prefix does not matter, on the one screen whose entire job is being trusted about a code. And `update_plant_settings` was handing Python booleans to INTEGER columns, which Postgres refuses with `DatatypeMismatch` and loses the **whole** save with it; `enable_packing` would have hit that the first time anyone unticked it.
- `tests/test_boot_paths.py` held the head revision as a literal, so it failed all three of its cases on the first migration added after it. A test that breaks on correct work, and whose fix is to edit the expectation, teaches you to edit expectations. It now reads the head out of `migrations/versions` — the one revision that is not some other file's `down_revision`.

- **The handbook is two parts.** Twenty-seven pages described eighteen screens at one weight, in the order they were built; to somebody deciding whether to allow this, that reads as a list of things they would be taking on. Part One is what runs and what comes out of it. Part Two is what a plant can switch on, each page headed with the fact that it is off. Role guides, readability, the test record and the unfinished experiments are appendices, because none of them is part of the decision. Every section header carries its status so the distinction survives somebody opening it in the middle, and the contents page says in one sentence that **Part One is the ask**.
- The cover said "Manufacturing Execution System". Accurate, and also a term that costs six figures elsewhere, which invites a question about authorisation before anyone has read a page. It says what it does now.
- Two pages of theme gallery became one page about reading a screen on the floor. Glove mode, light and dark under shop lighting, a measured contrast floor and resin texture are the floor's problems and worth the page; thirty-four of anything is mine and is not.
- **Four figures were lying**, which on a printed document does not fix itself. The page titled "The operator terminal", marked in service, illustrated itself with the assigned-runs block — the optional feature — so anybody reading the pictures took away the opposite of what the section says. The manager cockpit figure carried a heading renamed the same day. The pack-out figure carried two strings deleted the same day. The lot-gate figures still said "the bottom is stamped", the wording the floor corrected a day earlier. All re-shot.
- And the handbook's own overview had silently reverted to the old figures — eighteen screens, thirty-four themes — because the restructure script had grown a **duplicate dict key** and Python keeps only the last one. A page arguing against being impressed with itself was opening with two counts of exactly that.

- **Device Registry: a correction to yesterday's entry.** The comment I removed with its link said the page "has never existed". It had, and still does — 15 KB of working Device Gateway screen. The working copy the check ran in did not have it in `pages/`, and I recorded a conclusion about the repository from a fact about my own copy. It is unlinked on purpose, listed in `KNOWN_ORPHANS` with the reason, and described in the handbook's Appendix D so a reader who finds it by URL is not finding something the document left out.
- `test_links` no longer counts a page's link to **itself** as a route in. `Device_Registry.py` links to itself on line 71 and nowhere else, which registered as reachable and defeated the orphan check entirely — the precise failure that check exists to catch.

- **The folder is sorted, and the package that reaches the work PC is only the application.** Forty-one top-level `.py` files, of which about twenty were the app; the rest were screenshot scripts, document builders and a retired installer, sitting beside the code as if they ran on the floor. They now live in `dev/` (tooling) and `docs/` (handbook sources, figures and the finished PDFs), with `tests/` where it was, and `Move_To_New_PC.bat` excludes all three by folder rather than by a list of filenames that goes stale. Every moved script computes the project root from its own location rather than assuming it is being run from there. A `README.md` at the root says what is where and how to set a machine up.
- **First-time setup defaults to a clean database.** `Setup_On_New_PC.bat` refused to run without a backup and always restored it — which would have put the development database, demo operators and demo runs included, on the plant PC. A backup is now an offer: with none, the application builds its own schema and seeds one administrator account, three placeholder pumps and the downtime reasons, and the script says how to sign in and what to do first. With one, it asks. A missing `.env` is created from the template with instructions rather than treated as proof of a broken package. `.env.example` no longer asks for an email account, since nothing sends one.

- Suite: 894 assertions across nine files, 18 screens rendered, 45 browser checks. 957 total.

## 3.11 — Thursday, September 3, 2026
**A readiness pass before testing at the plant, and three corrections from the floor**

No new features. The task was to confirm the build is ready to take to the floor, and the honest answer was not yet: four defects that the existing suites could not see, three of them because the tests stub out the very thing that was broken. Then three corrections that only somebody who works the line would catch — the handbook describing a history the plant does not have, and a check that had been skipping a whole container format on a wrong assumption about it.

- **A restored backup would not have started.** `init_db()` had three cases and only two of them ended up at head: a database with the app's tables but no recorded revision — which is what an older backup restored onto another machine looks like — was stamped at the baseline *instead of* being upgraded, not before it. The app then ran the rest of that boot against a schema seven revisions behind the models and died on the first settings read with `column plant_settings.shift_count does not exist`. Stamping says where a database already is; it is not a substitute for bringing it up to date. Now it stamps where needed and always upgrades afterwards, and the stamp is a plain INSERT rather than `command.stamp`, because Alembic's environment is not re-entrant and this path has to run a real upgrade straight after. **This is the path `Setup_On_New_PC.bat` takes**, whose own comment was relying on the behaviour that did not exist.
- New `tests/test_boot_paths.py` drives all three states in separate processes — empty, pre-Alembic, and stamped-but-behind — and checks each reaches head with the columns the models select on. The behind case additionally seeds a user, a production log and a plant setting first and counts them by identity afterwards, because "reached head" would also be satisfied by a migration that quietly emptied a table.

- **The IT Admin console was dead for every admin.** One line in its sidebar linked to `pages/Device_Registry.py`, a page that has never existed — the Device Gateway is a backend package with no screen. `st.page_link` raises on a target it cannot find, and the navigation renders near the top, so the whole console was a stack trace. The page sweep could not catch it: that harness stubs `st.page_link` out, because AppTest runs one script with no multipage registry behind it. Found by opening the page in a browser.
- New `tests/test_links.py` reads the source instead of rendering it, so a stub cannot hide anything: 178 navigation targets across 20 files, every one confirmed to be a real file. It flags pages nothing links to as well, which found a second one — the **Theme Gallery had been built and then left with no route in**, reachable only by typing its URL. Now linked from the Manager Cockpit. Its exemption list is empty and an entry has to still be an exemption: a name left there after a page gains a link would go on excusing it for ever, including the day something removes its only link. That check failed on its own first run and was right to.

- **Every form label in the app was at 1.4:1 on the dark themes.** Streamlit colours anything a theme does not, using a value chosen for its own light base theme — so the widget label above every control, the navigation links, and the popover trigger all kept a near-black default on a dark ground. Measured in a browser: nav links **1.35:1**, widget labels **1.14–1.68:1**, the *Account & Preferences* button **1.01:1**. Worst on a phone, where the six nav buttons are the entire navigation. The contrast audit never saw it because it checks the palette the themes define, and this was the text they *don't* define.
- Fixed once in the shared base stylesheet rather than in thirty-four themes. The sidebar container also had to be reconnected: Streamlit sets a colour on it, which cut the inheritance chain from `.stApp`. Colouring the link alone was not enough either — Streamlit wraps the label in its own markdown container and colours that, so the descendants inherit too. The popover trigger needed a surface as well as a colour, since it keeps Streamlit's near-white button background that no theme paints over; it now gets the same translucent pill as the nav links, with the light themes correcting both together. Measured after, across the range — Forge, Matrix, Neon Cyberpunk, Dracula, Nordic Frost, both high-contrast pairs and two light themes: **9.1:1 to 18.9:1**, every one above the floor.

- **New `tests/smoke_browser.py`** — the gap all three of the above fell through. `test_ui` executes the operator page but renders nothing; `test_pages` proves each page builds. Neither opens a browser, so neither can see a control that is off-screen, a click that does nothing, or a page that threw after it rendered. This drives a real browser through an operator's first hour: sign in, open all six screens and look for a stack trace on each, set the form to a station that actually has an active run, get the lot wrong and confirm the pour stops with submit disabled, get it right and confirm it clears, type a check weight and watch it judged, then do the sign-in again at 390×844 and confirm the sidebar is not covering the page and nothing scrolls sideways.
- Two of its own assertions were wrong before they were right, and both were worth the correction. The lot-gate checks were judging a form that had never been pointed at a run — with no matching run there is no gate, which is correct behaviour reported as a bug. And "the expected lot is never printed" fails as an admin *by design*: masking is role-dependent, because an operator must read the cartridge while a manager reviewing a flagged pour needs to see it. The check now asserts whichever is right for the account it signed in as.


- **RPS jugs are gated like every other format now.** They were the one exception, on the understanding that bulk jugs carried no lot label. They always have — and the plant has since made the tag going on before pouring starts a rule, which is what let the check be turned on there. `GATED_FORMATS` now covers all four, and the exemption that unmasked the expected lot on RPS is gone too: showing a jug's lot on screen would defeat the check on that format exactly as it would on any other.
- The wording follows the container, and only the noun differs. Cartridges and jugs carry the same kind of lot label in the same place — on the bottom of the empty, applied before it is filled — so the check, the instruction and the action are identical. `crud.container_words` returns the strings that change and the form asks for them once; on a jug the section reads *Jug Lot Verification*, *hidden on purpose — read the jug, not the screen*, *Turn the jug over. The lot label on the bottom reads L- followed by the lot*, and the field is *L- — lot on the jug bottom label*. It follows the Container Format picker, not the page: switching format mid-session flips every one of those strings, which is asserted by switching it back and forth on one instance and reading what the page says each time.
- Two earlier passes at this got it wrong in opposite directions — one sent operators hunting for a tag on the side of a jug, the other invented a distinction between a stamped cartridge and a labelled jug that does not exist. Both would have been noticed at the pump and nowhere else, which is the argument for keeping the difference down to one word. The photo prompt, the outstanding-item list and the note written onto a flagged log all follow it too, so nothing on the screen calls a jug a cartridge.
- Asserted on the rendered form, not on a constant: the jug gets a lot field and loses the free-entry one, the instruction points at the label on its bottom, submit stays blocked until it is read, a wrong label produces the stop screen, the right one clears it, and the expected lot stays masked for an operator throughout. `test_workflow`'s RPS run carries a real lot and its counts move accordingly — one more full check, one more verified log — because the old numbers were only correct while that pour was ungated.

- **Corrections to the handbook, from the floor.**
- It opened by describing an Excel tracker the pouring station used to run on. There was never a tracking system for pouring — the spreadsheet was a prototype of this, not a predecessor to it — so the framing invented a history the plant does not have. Section 1 now says what is true: counts, downtime, changeovers and lots lived on paper and in people's heads, and this is the first record of any of it.
- The repository is not the reader's business, so the line about secrets being kept out of it now says what it means to a manager: credentials live in a configuration file on the machine, not written into the program.
- Stats that had drifted since they were written: three shifts became two (and a setting, not an assumption), twenty-four themes became thirty-four, and the release check count is now measured rather than remembered.

## 3.10 — Wednesday, September 2, 2026
**Fill-weight capture, two shifts, a theme engine with light themes, chip textures, and the floor-usability pass**

- **The app has always known the target fill weight and never once recorded a measurement against it.** `resin_specs` carries the target and the tolerance window — 1110 g, accept 1100 to 1115 — so it could say how many units were poured but not how much resin went into them. Added an optional check-weight box to the hourly pouring form, three columns on `production_logs` (Alembic `0006`), and a fill-weight section in Analytics.
- **Passing the check and giving away resin are the same reading.** A pump set to run safely clear of the low limit sits above target on every single cartridge — inside spec, passing every check, and handing over free resin on every unit. Four of the sixteen specs make that worse by being lopsided (Clear V5 and Grey V5 allow 10 g under target and only 5 g over, so the safe place to sit is nearer the ceiling), but the giveaway does not depend on that: it happens on a symmetric window too. Every gram above target is about 0.09% of the fill, which is 4 kg per thousand cartridges at 4 g heavy. Nothing in the app could see it before, because the target was displayed and never compared against anything.
- **The reading is optional and can never block a submission.** The lot gate stops the line because a wrong lot is a defect; a heavy cartridge is information. Make a weight mandatory and within a week it's the target typed from memory on every log — and a column full of `1110` is worse than an empty one, because it looks like data. Sparse and honest beats dense and fabricated. **And it is never pre-filled**, for the same reason the run card had to stop printing the lot the gate was hiding: a box that already contains the right-looking answer gets accepted, not measured. Both rules are asserted against the real rendered page — the tests drive the actual form and check that submit stays enabled with the box empty, and stays enabled when the reading is out of band.
- Deliberately one field, not the three the paper form asks for. Three cartridges weighed in the same minute mostly measure the scale's noise; the variation worth catching is between hours, not within a minute. One reading an hour is a sample of that hour, which is why the analytics weight each reading by the units logged alongside it — that's what turns "+3 g" into kilograms. The verdict is judged against the resin's own window at capture and stored, so editing a spec later can't retrospectively re-judge readings somebody already took.
- Live feedback as the number is typed — in band, or how far outside and that it's worth telling a lead. An optional field that swallows the number teaches people to skip it; one that answers tells them something about the pump they're standing at. The scatter plots deviation rather than absolute grams, because each resin has its own target and raw weights would stack unrelated products on one axis, with out-of-band readings on their own trace so they don't vanish into a few hundred points.
- Worth noting the endgame this is a bridge to: the `serial_ascii` adapter in the Device Gateway was written for exactly these bench scales. If they have a serial output the weight arrives with no operator effort at all — and these manual readings are how that automated capture would be validated, since you need known-good numbers to check it against.

- **The plant runs two shifts, not three.** The app assumed three and offered "Shift 3" in every picker. Rather than hardcode two — which only moves the wrong assumption — the count is now a plant setting (Alembic `0007`, default 2), and every picker and the gateway's shift resolver derive from it. Logs written when three shifts were offered are real production: they keep their label, stay in every report, and a record that already holds a retired shift still offers it in the dropdown, so opening an old row and saving cannot silently reassign somebody's work.
- **Found while generalising it: the gateway's shift resolver could not answer 01:30.** It sorted the configured start times and took the largest match — but 01:30 is earlier than every start time, so the answer fell out of list ordering rather than out of any reasoning about midnight. A shift boundary is a wrap-around, not a sort. Now the last shift of the day owns everything from its start until the first begins next morning, asserted across the whole clock on both two- and three-shift plants.

- **A theme engine, and ten new themes — six of them light.** Not one of the original twenty-four was light, which is a real gap on a brightly lit pouring floor where a dark screen is a mirror, and it bit again when the handbook had to be printed. New themes are now a palette of about a dozen colours rather than fifteen hand-written CSS rules, so a new component is styled once instead of twenty-four times. The existing twenty-four are untouched on purpose: people have preferences saved against them by name, and rewriting somebody's design work to gain tidiness would risk twenty-four regressions.
- Light: **Daylight**, **Forge Light**, **Paper White** (warm and flat, closest thing on screen to the printed sheets this plant still runs on), **Blueprint**, **Clean Room**, and **High Contrast Light**. Dark: **Nordic Frost**, **Solarized Deep**, **Workshop Retro**, and **High Contrast Dark**. The two high-contrast pairs are built to the accessibility floor rather than to taste, which also makes them the best choice under glare or at the end of a shift.
- **The contrast checker found two real failures in the existing themes.** Card labels were 3.9:1 in **Default Dark** — the theme most people are looking at — and 3.0:1 in **Dracula**, both below the 4.5:1 floor for body text. Fixed, Dracula's within its own palette so it still looks like Dracula. All 34 themes now clear AA, and a Theme Gallery page renders every component in the current theme and runs the audit on demand, so this is something you can see rather than something that was checked once.
- **Rebuilt the handbook in a light palette for printing.** Management is printing it, and a 24-page document of dark pages is a solid block of toner that bleeds through the sheet. The screenshots are genuinely dark — every one of the app's themes was — so rather than misrepresent the product I lifted the black floor on the captures, which took ink coverage from about 95% to 74% with every pixel of content unchanged. The closing "open questions" section came out.

- **Resin chips carry a texture as well as a colour.** Measured across the palette, five pairs sit within a perceptual distance of 5 — the same colour to the eye. Clear V4 and Rigid 4000 are 1.9 apart; Black V4 and Tough 1500 are 4.4. Those colours came off the plant's own sheet, where each sits beside a full row of text; shrunk to a chip, colour was being asked to carry more than it can, and a Clear/Rigid mix-up is exactly what the lot gate exists to catch. The texture is derived from the resin *family*, so Clear V4 and Clear V4.1 still match — same material, one revision apart — while Clear and Rigid cannot. It also survives greyscale printing and colour vision deficiency.
- Patterns are **assigned rather than hashed**. Hashing gave a stable texture but an arbitrary one, and it collided exactly where it could least afford to: Rigid 10K and Rigid 4000 are 3.4 apart, carry target weights 370 g apart, and drew the same texture. Now each family takes a texture no perceptually-near neighbour is already using — correct by construction, and it stays correct when a family is added.

- **Glove mode.** Operators handling resin wear nitrile; touch still registers but precision drops, and the pouring form asks for number steppers and a lot field. A toggle pushes every target past the accessibility touch floor and scales the type. Stored against the *terminal*, not the account — glove mode is a property of where you are standing, not of who you are, so a shared floor terminal keeps it for whoever signs in next while the same person at a desk gets the density back.
- **Night dimming**, derived from the plant's own configured shift times rather than a hardcoded hour, since "night" here means "not the day shift". A gentle brightness and warmth reduction rather than new colours, so it composes with all 34 themes; photographs are exempted so a stamp under review keeps its true colour. The alternative people reach for otherwise is turning the monitor down, which destroys the colour coding the lot check depends on.
- **Undo on your own last log.** A typo — 2500 where 250 was meant — needed a manager to open Log Management, which means the wrong number sits in every dashboard until one is found. Now the operator can take back their own most recent entry for two minutes. Own row only, checked against the log rather than trusting the caller; latest row only, since undoing an older one would silently change what newer ones were credited against; and never a flagged log, because that flag is a cartridge problem somebody may be reviewing. Run progress is recomputed from surviving logs rather than subtracted.
- **Focus mode.** During a pour the operator is at the pump, not at the screen, and the four things they need mid-run — resin, lot, count so far, how many left — are scattered across a card, a progress bar and a form at a size that means walking over and leaning in. One toggle replaces the page with those four, large enough to read from across the station. A toggle rather than a separate page, because the moment they need it is the moment they need to log.

- **The pouring form now says whether the log actually saved.** The write was unguarded: if the database was unreachable the page raised or silently re-ran, and an operator who is unsure re-submits. A duplicated hourly count is worse than a missing one, because nothing about it looks wrong afterwards. A failure now says plainly that nothing was recorded, so nothing is duplicated, and to try again — which matters on a network that drops in parts of this building.
- **Pulled the repeated markup into `components.py`** — cards, stat tiles, notes and section headers were hand-written HTML in f-strings, copied page to page and drifting a little each time. That is the same duplication that once put a 131-line navigation block into eleven files and hid a crash in eight of them. Escaping happens inside the component, the same rule the resin chip already follows.
- **An empty-state pass.** Five pages rendered *nothing at all* when they had no data — Scrap Intelligence, Historical Trends, Cleanliness, and both charts on the yield page. Most of the rest said something like "No assigned runs currently active", which states the obvious and leaves the reader stuck. Every empty screen now says what will make it fill up and, where there is one, the concrete next step. Deliberately not styled as an error — having no data yet is normal on a system installed last week, and painting that red teaches people to ignore red.

- **Visual regression screenshots** (`tests/visual_regression.py`). The page sweep proves every page renders without raising, and it has caught real crashes — but a page can render perfectly and still be wrong: a card that lost its border, a chart that came back empty, a nav bar that wrapped. None of that raises, and on the wall display it might go unnoticed for days. This drives a real browser through every page and diffs against the last approved set. Verified both directions: a deliberately broken card reports 6.5% of pixels changed while an untouched page reports 0.00%. Comparison has a tolerance rather than demanding an exact match, because antialiasing shifts a pixel or two between runs and a check that cries wolf gets switched off within a week. The baseline is not committed — it is photographs of one database on one machine, so run it once with `--approve` on your own install and it becomes meaningful from then on.
- **Found in a browser after the tests passed: every light theme rendered its CSS as visible text.** Streamlit passes stylesheets through markdown, and CommonMark treats a four-space-indented line as a code block — so an indented `<style>` *appended after* other content is displayed as source instead of applied. The twenty-four hand-written themes were never bitten because theirs comes first, where the HTML-block rule wins. Fixed by emitting generated CSS at column zero, with a regression test that asserts precisely the real condition rather than banning indentation outright.
- **And one in the test suite itself:** `test_resin_colors` pinned the schema to `head`, so adding migration `0006` broke it — a false alarm about an unrelated migration rather than a real regression. It now upgrades to `0005` specifically, since that is the revision it is actually testing.

- **Operators are on their own phones, not a station tablet — and the app was pushing the page off the screen.** `initial_sidebar_state="expanded"` is an instruction that ignores the screen it lands on: the sidebar is a ~320 px overlay, so on a 390 px handset it covered four fifths of the page and the first action of every hour was closing something nobody opened. Two files set it; every other page already left it at the default. Now `auto` — expanded on a desktop and the wall display, collapsed on a phone. Measured rather than assumed: the sidebar occupies 1 px of 390 after the change.
- **The pump form is now a button inside the MES, not a sticker on the pump.** Scanning the QR code works but it is a one-way trip — the phone navigates away from the MES and the way back is the browser's back button, which costs the session and whatever was half-typed. A link button opens the same form in a second tab, so the MES is never left and closing the form puts the operator back mid-log. It also beats walking to the pump, since they are already holding the phone. The address is a plant setting (Alembic `0008`), not a constant, because this application does not own that form and whoever does can move it; no address configured means no button, which is right for a plant that has no such form.
- Addresses are checked where they are typed rather than where they are used. A device whose adapter throws — unreachable host, wrong COM port, bad credentials — doesn't take the rest of the gateway down: that worker logs it, flips the device to Error with the message stored, and retries with backoff up to a minute. It's meant to run on a floor PC with actual network and COM-port access to the equipment, which isn't necessarily the machine Postgres is on, so I also wrote the discovery piece that lets it find the database over the local network instead of hand-editing a config file on every PC.
- New admin page (`Device_Registry.py`) for finding, registering, test-connecting and tag-mapping that equipment. Three tabs: every registered machine with live status and last-seen time and an inline tag-map editor; an add/test tab that renders protocol-specific connection fields and has a Test Connection probe showing the raw response *before* anything gets saved; and a readings tab charting a device's history over a chosen window. The live probe matters — being able to try a regex against real serial output before committing a tag map is the difference between an afternoon and a week.
- Schema for all of it went in as Alembic migration `0002`, chained onto the baseline and purely additive — no existing table touched — with foreign keys tying a device to the same station and reactor rows the rest of the app already keys off. It runs automatically on next boot through the `init_db()` path from the day before, so there's no manual migration step. Also wrote `README_DEVICE_GATEWAY.md` with the architecture rationale and a suggested rollout order: start with a bench scale over serial, which is the cheapest thing to be wrong about, before touching the filling HMI.

## 3.6 — Saturday, August 29, 2026
**Migration framework, real password hashing, referential integrity, and the logging to see any of it**
*Three releases this day.*

- **Replaced the way the database schema changes.** `init_db()` had grown a hand-maintained list of thirty-odd raw `ALTER TABLE` strings, all wrapped in one silent `try/except` that couldn't tell "this column already exists" apart from a genuine failure — so a migration that actually broke looked exactly like one that had already been applied. Swapped it for a proper Alembic migration history. `init_db()` handles the one-time transition itself: a brand-new database runs the full baseline from scratch, an existing production database gets stamped at baseline instead of re-running `CREATE TABLE` against tables that are already there. Schema changes from here are a generated revision file, not another appended string.
- Hit a `configparser` crash in the Alembic setup the moment a database password contained a URL-encoded character — a `%21` for a `!` gets read as an interpolation token. Escaped literal `%` as `%%` before handing the URL to Alembic's config. Small, but it would have stopped the app dead on any machine with a password like that.
- **Moved PINs to bcrypt.** They were raw SHA-256 with no salt, which is fast to compute and therefore fast to attack in bulk. Now salted bcrypt across creation, PIN changes and login. Legacy accounts that predate the change are detected and get a clear "needs an IT admin reset" message rather than a confusing failed login, so nobody gets silently locked out by the upgrade.
- **Added account lockouts.** Five consecutive failed PIN attempts locks the account for fifteen minutes. Also made an unknown username return the identical "invalid credentials" message as a wrong PIN — before, the two responses differed, which quietly told anyone probing the login screen which usernames were real. Successful logins and admin resets both clear the counter.
- Gave IT somewhere to undo that: the staff table in the Admin Panel now shows a live locked/unlocked column and a count of locked accounts, with an Unlock button so a lockout can be cleared instantly without also resetting the operator's PIN and interrupting their shift.
- **Fixed the bug where renaming an operator split their history in two.** Every log stored the operator as a plain string, so the moment someone's name changed, all their old logs were orphaned from all their new ones and Analytics showed them as two people. Root fix was adding real foreign keys — `operator_id`, `pump_station_id`, `resin_spec_id`, `sender_id`, `current_resin_id`, `assigned_pump_id` — across production logs, downtime, assigned runs, checklists, cleanliness audits, floor messages and reactors, all nullable with `ON DELETE SET NULL`, so deleting a user or a pump can't blow up on historical rows. Kept the legacy name columns alongside, for backward compatibility and for system-generated rows with no matching account.
- Wrote a backfill pass that resolves the existing free-text names against real rows and fills in those new keys on data already in the database. Safe to re-run, and guarded so it runs once per server process rather than on every page load. New keys are worthless if they're only populated going forward.
- Then wired the resolution into every write path — the eight functions that create logs, downtime, audits, runs, checklists, messages and reconciliations all now store the matching key alongside the string at the moment of writing, so the backfill never has to run for that data again.
- With the keys in place, the Analytics operator matrix and the TV dashboard's top-pourers leaderboard now group by resolved identity mapped to the person's *current* display name, so one person is one row regardless of what they were called at the time.
- Fixed the Historical page, where the operator filter and the "Total Output by Operator" chart disagreed after a rename — the chart consolidated by identity while the filter still matched the raw logged string, so picking someone from the dropdown showed less than the chart claimed they'd made. The filter now has a key-based path, with exact-string match kept as a fallback for legacy and deleted accounts.
- **Fixed backups, which could have been pointed at the wrong database.** `create_database_backup` / `restore_database_backup` had `localhost`, `postgres` and the database name hardcoded, plus a Windows-only `pg_dump.exe` path, and ignored the configured database URL entirely. Point the app anywhere else and the backup silently backs up something else. Now it derives host, port, user, database and password from the real connection URL, and finds `pg_dump`/`psql` via an optional env var on Windows or the PATH elsewhere. Also deleted a stale duplicate copy of both functions that had been quietly shadowing the real ones through the import facade — the kind of thing where you fix the function and nothing changes because the app was never calling it.
- **Added actual error logging** (`app_logger.py`) — rotating log file plus console, with a guard so Streamlit's constant reruns don't stack a new handler every time a page re-executes. Then went back and wired it into the exception handlers that had been swallowing failures silently: the FK backfill, resin spec creation, suggestions, reactor creation, and above all backup/restore, which now logs what `pg_dump` actually said on stderr instead of failing with no trail at all. They still fail safe for whoever's on the floor; the difference is I can now see what happened.
- **Broke up the `database.py` monolith.** It had passed a thousand lines and held the engine, every table definition, every query and the OS/file helpers all in one place. Split into four: `db_core.py` (engine, sessions, connection URL), `models.py` (table definitions), `crud.py` (all the reads and writes), `utils.py` (filesystem work and backups). Then left `database.py` in place as a thin import hub, which is why not one page in `pages/` had to change — every existing `from database import ...` kept working, so a structural refactor of the whole data layer shipped without touching the front end at all.
- **Swept every blocking `time.sleep()` out of the request path.** They were there to let a message be read before a rerun, but Streamlit serves on a thread, so each one froze the server for everyone else on the floor too. Replaced with immediate reruns, and replaced blocking success messages with toasts that survive the rerun — so the page reloads instantly and the confirmation still appears. Rewrote the auto-login check, the logout sequence and theme switching the same way.
- Fixed the boot order, which had been working by luck: catalog constants are now defined above the seed functions that use them, and database initialization moved to the very end of the load cycle rather than the middle.
- Wrote `create_admin.py`, a standalone terminal script that reads the environment config and force-creates a properly hashed superuser. Exists for exactly one situation — total lockout or a wiped database — but that's a situation where having no way in at all would be the end of the app on that machine.
- **Fixed the login screen's theme flicker.** The saved theme lives in a browser cookie, and the cookie read lags the first render, so the screen painted in the default theme and then jumped to yours — and the previous workaround for that was a blocking sleep. Added a session-state lock so the theme is read once and trusted, and made a manual theme change trust memory rather than waiting on the cookie round-trip. Also gave the login screen's widgets explicit unique keys, which stopped the duplicate-element errors that were showing up during token and theme generation.
- **Made profile pictures actually render.** The avatar filename had been saved to the database on every upload since the feature shipped — and nothing ever read it back. Authentication, session lookup and the auth check all left it out of the session data, and every sidebar header drew a hardcoded 👤 emoji instead. Fixed across all sixteen pages, with one shared helper resolving a stored filename to a real file so a deleted or missing image degrades to the emoji instead of erroring. The Account & Preferences popover now previews the current avatar, and the IT Admin console — which had never had an uploader at all — got one.
- Chat threads had the same class of bug from the other direction: manager and operator messages drew a fixed icon per role, so every manager looked like the same person. The chat history query now joins on the sender's account to pull that person's own avatar, falling back to the role icon for senders with no picture or for messages that predate the foreign keys.
- The feedback inbox now shows the submitter's avatar too. Suggestions have no key back to an account — just the typed name — so it matches best-effort on current display name and simply shows nothing for a name that no longer resolves. Same fallback pattern used everywhere else legacy string-only data shows up.
